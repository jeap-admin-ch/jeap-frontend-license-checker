# AGENTS.md

Guidance for AI coding agents working **in this repository**. For how to _use_ the tool in a
project, read [README.md](README.md) and the [docs/](docs/) folder instead.

## Project

`@jeap/jeap-frontend-license-checker` is a Node.js command line tool that checks the licenses of
the npm dependencies installed in a frontend project against a license policy, and generates the
third-party notice file for them. It replaces the license checker the jEAP frontends used so
far.

Two properties are the reason it exists and must not be given up:

- **Wildcard exceptions work for scoped packages.** A package key is split at its **last** `@`.
  Splitting at the first one yields an empty package name for every `@scope/...` package, which
  is the defect of the tool this one replaces.
- **The policy ships with the tool.** Accepted licenses live in `src/default-policy.ts`, not in
  each project, so a policy change is a version bump instead of an edit in every repository.

## Build & test

```bash
npm ci
npm run format        # Prettier --write (or format:check to verify only)
npm run lint
npm run test
npm run build
npm run notices       # regenerate THIRD-PARTY-LICENSES.md
```

**Before every commit, run `npm run format` and `npm run lint`.** The "Lint and format" CI job
runs `npm run format:check` followed by `npm run lint` and fails the build on any deviation.

## Conventions

- **No runtime dependencies.** `dependencies` must stay empty; the packaging job fails
  otherwise. Anything needed at run time is implemented here or comes from the Node standard
  library. Development dependencies are unrestricted.
- Node.js 20.11.0 is the minimum. Do not use APIs that are newer without raising `engines` and
  the CI test matrix together.
- The output is CommonJS, because the tool is executed as a `bin` script in projects with mixed
  module setups.
- `test/fixtures/project/node_modules` is committed on purpose. It is test input, not an
  installed dependency tree; never add it to `.gitignore` and never run `npm install` in it.
- Public exports go through `src/index.ts`.
- Keep code comments in English, and say why rather than what.

## Behaviour rules

- Never let a package pass silently. A package that is not covered by the policy is either an
  explicit exception with a reason, or a problem.
- A dual licensed package is accepted through a permissive alternative, but must stay visible in
  its own report section. An exception for such a package takes precedence over the automatic
  choice, so documenting the decision does not make the exception count as unused.
- License text detection is a fallback for packages whose manifest carries no usable license,
  never an override of a declared license. Detected results are marked as such in the report.
- A URL is not a license: a `license` object with only a `url` results in an unknown license.
- Exit codes are part of the contract: `0` passed, `1` policy violated, `2` bad invocation or
  configuration.
- Changing `src/default-policy.ts` changes every consuming project. Adding an accepted license
  is a minor release; removing one is a major release, because it breaks builds.

## Testing conventions

- Every behaviour a project could rely on has a test. A new license detection rule needs a
  fixture package under `test/fixtures/project/node_modules/`.
- The two regressions this tool exists for have named tests and must keep them: a scoped package
  stays exempted across a version bump, and an unused exception is reported.
- Tests use the Node test runner and plain assertions. Do not add a test framework dependency.

## Commit and branch conventions

Keep commit messages short and concrete.

If the branch name contains a JIRA issue id, use it as the commit prefix:

```text
JEAP-1234 Added scope wildcard exceptions
```

Do not use generated commit messages that include long summaries, tool traces, or unrelated
context.

## AI agent rules

- Prefer small, focused changes.
- Do not add runtime dependencies.
- Do not change the license policy without updating [docs/policy.md](docs/policy.md) and the
  changelog, and without considering whether it is a breaking change.
- Do not weaken the exception matching rules; they are the reason this tool exists.
- Do not edit `THIRD-PARTY-LICENSES.md` by hand; regenerate it with `npm run notices`.
- Update tests and docs together with behaviour changes.
- Run `npm run format` and `npm run lint` before committing.
